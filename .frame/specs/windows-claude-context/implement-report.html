Put .frame/bin on Windows PATH and name what lives there

6968791pass npm test 533 tests pass, 0 fail (19 in test/launchEnv.test.js, 8 of them new)
What changed

launchEnv.prependFrameBin lost its supportsWrappers gate, so .frame/bin now leads the PATH of every PTY Frame spawns on Windows too — the ';' separator the function already carried finally gets reached. Two siblings joined it: wrapperFamily(platform) answers 'posix' or 'cmd', and wrapperFileName(toolId, { platform, canPassPaths }) returns the filename a tool's wrapper takes here, or '' when it earns none.

Why

The gate was a category error: supportsWrappers asks whether this platform gets a POSIX wrapper for every tool, and PATH ordering is a different question — a .frame/bin that happens to be empty is a harmless first entry. wrapperFileName takes canPassPaths rather than a hardcoded 'claude only' list because a file-taking prompt flag is precisely what lets a batch wrapper stay plain; canPassPaths defaults to false so Windows opts a tool in explicitly and Codex/Gemini keep today's behaviour by construction. Both new functions take platform as a parameter, so Windows behaviour is asserted from a Mac.

Teach Claude's launch to pass paths instead of prose

defcd9bpass npm test 545 tests pass, 0 fail (12 new in test/aiToolLaunch.test.js)
What changed

Claude's injection record gained promptFileFlag: '--append-system-prompt-file'. prepareLaunchAssets now also returns preambleRel and settingsRel — the same two files as project-relative, forward-slash paths. A new exported pure inlineInjectionFlags(tool, assets, platform) composes the wrapper-less branch and getLaunchCommand delegates to it, dropping its own flags.push pair and the now-unused `declared` local.

Why

The composed line is typed into the PTY, and the preamble is 9 lines with 6 backticks: cmd.exe submits at the first newline and PowerShell reads a backtick as an escape, so --settings — and with it the spec-hint hooks — is the first thing lost. Two paths make the line single-line and quote-free. The paths are relative because the PTY's cwd is the project, which sidesteps a space in the path and the backslash a POSIX shell would eat. The file flag is chosen only where !supportsWrappers(platform): it has no --help row of its own, so an older CLI rejects it outright, and the POSIX path that works today must not acquire that version dependency (C3).
