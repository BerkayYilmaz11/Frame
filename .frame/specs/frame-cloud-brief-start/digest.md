Start Work on an open, shaped work brief begins one part. It reserves every part's spec slug or task id in one `brief.start` (the brief goes Active), cuts the chosen part's branch from the brief's target or a picked base, writes only that part (`spec.md` + `status.json`, or a `tasks.json` row), and opens its lane (`/spec.plan` or the task run). A started brief's other parts read Not started · Begin on the card, and Begin does the same for that part under its reserved ref, with no cloud write. This machine records which part it began on which branch (`<userData>/cloud-starts.json`), so rows read On `<branch>`. A record whose branch is gone is ignored.
Why this path: the first build wrote every part onto one branch named for the chosen part (plus Create only). The walk showed that pins all parts to one branch: the next part lands on the wrong branch or drags untracked folders across a switch. One part per branch gives one PR each, and parallel parts are Orchestrate's job (shown, disabled). A FrameCloud per-part field was rejected for the machine-local record, which fits a shared, team-visible brief better. No automatic commit: the lane commits, and a dirty folder gets the dirty warning.
Names: Shape writes a short kebab-case `key` per part (FrameCloud `brief_part.key`), and Frame suggests the slug, the task id and `<prefix>/<key>` from it, editable. Without a key, the title's slug is cut at a word boundary (32 characters for a branch, 48 for a slug). The branch row is an editable name chip plus "from `<base>` ⌄", local then origin.
Rules for later: every local check runs before `brief.start` (cloud first, then stash, branch, files); a failure after the checks is `partial` and names the missing part. The renderer is untrusted: main re-reads the brief and re-checks the base, branch and dirty state. Never stash without consent. The card learns of a deleted branch only on its next load.

Chain: spec.md → plan.md → tasks.md → outcome.md
